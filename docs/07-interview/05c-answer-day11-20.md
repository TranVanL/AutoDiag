Day 11 : 
1. Vì sao phải đọc perf JNI trước khi code native bridge? 

Must broaden the horizon about perf JNI because inside process that communicate between two worlds Java and C++ , has a lot of problem you must notice : 
1. Overhead call : Every call from Java to C++ or vice versa , it require a huge time , cost , ... . -> avoid call too much or call unefficient
2. Object transmit : Cost and time to handle object through two worlds -> Structure object paracable 
3. Thread problem : Thread personal from C++ cannot access to some object private in Java like JavaEnv* that point to the table contain all of JIN Bridge object -> need to AttachThread to access class and method , DetachThread when terminate 
4. JNI reference : To get global access , have to change from localRef to GlobalRef . But it require a management by hand , Different with Java object normal that use Garbarge collection 
5. Exception : C++ JNI cannot handle exception -> IT will waste a lot of time and cost to become an exception Java and JVM will handle it -> Big problem 

2. JNI_OnLoad nên cache những gì và vì sao không nên FindClass lặp lại ở runtime? 
Should cache the class callback and method of it 
-> Really efficient when call a huge time and one time cost to find class and method 
- Find Class repeat in runtime will waste resource and maybe cause issue if thread still isn't attached

6. JNI local ref và global ref khác nhau ở điểm cốt lõi nào? 
- Scope and lifecycle

7. Vì sao FindClass trên worker thread có thể fail? 

Because , worker thread can be created by std::thread by C++ code . It isn't assigned JavaEnv* - pointer represent for table of entire JNI bridge object 
When request across through BInder IPC , a Binder thread will be get from pool and JVM will assign a JavaEnv* for it

-Response path

Positive response: ServiceID + 0x40 + PropertyID + Data.

Negative response: 0x7F + ServiceID + NRC.

Decode: client parse response, map sang model (success hoặc error).
